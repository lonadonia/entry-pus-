# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An automation bot for Freelancer.com **design contests** and **normal projects (bids/proposals)**. The contest side scrapes new contests, analyzes each brief with the configured chat model, generates entry images with the configured image model, and auto-submits them via headless-browser automation. **Which AI runs is configuration, not code**: the AI Agents page picks one provider and one model per task — APIDot, Kie.ai or APIMart (GPT / Claude models listed live per key) for chat; APIDot, Kie.ai, PoYo, KovAPI or APIMart for images — see "AI Agents" below. The projects side (see "Projects / Proposals workflow" below and `docs/PROJECTS_WORKFLOW.md`) reads normal projects for a configurable search through Freelancer's own JSON API, analyzes them against the account's real Freelancer.com profile, generates reviewed bid proposals with deterministic pricing/duration, and submits bids through an authenticated browser session. On top of the buttons, Celery beat drives two unattended jobs: a **daily project discovery** at a per-Space local time (default 23:00 Africa/Casablanca) that files the projects *published that day* and sends the eligible ones to analysis, and an **automatic cleanup** that deletes Skipped/Failed projects 24 h after they entered that status. Neither ever submits a bid. All driven from a Flask web dashboard with live updates; the dashboard opens with "Projects · Today" analytics. It is **multi-tenant**: every piece of data is scoped to a "Space" (workspace/tenant), each with its own contests, projects, settings, API keys, and Freelancer login cookies.

Stack: Flask 3 + Flask-SocketIO (eventlet) + SQLAlchemy, Celery + Redis, PostgreSQL (SQLite fallback), Selenium / undetected-chromedriver, APIDot / Kie.ai / APIMart for LLM analysis and APIDot / Kie.ai / PoYo / KovAPI / APIMart for image generation, served by gunicorn behind nginx, packaged with Docker Compose.

## Commands

Everything runs through Docker Compose (services: `postgres`, `redis`, `web`, `celery_worker`, `celery_beat`, `nginx`). Run exactly one `celery_beat`.

```bash
docker compose up --build -d          # build images + start the full stack
docker compose logs -f web            # follow gunicorn logs
docker compose logs -f celery_worker  # follow the task pipeline (most useful log)
docker compose ps                     # service / health status
```

**Code is baked into the image at build time** (`COPY . .` in the Dockerfile). Only `./storage` and `./app/static/temp` are bind-mounted. Editing a `.py`/template on the host does **nothing** to a running container — you must rebuild:

```bash
docker compose up -d --build web celery_worker celery_beat   # rebuild after any code change
```

**Every package is locked in `constraints.txt`** and applied at build time (`pip install -r requirements.txt -c constraints.txt`). `requirements.txt` only ever pinned direct dependencies, so a routine rebuild on 2026-10-30 silently pulled SQLAlchemy 2.1, whose default PostgreSQL driver is `psycopg` rather than the `psycopg2` this app ships: `web` crash-looped at boot, about 12 minutes down, while the whole SQLite test suite stayed green. Old images are garbage-collected as soon as their containers are replaced, so **there is no retagging your way back** — roll forward. Upgrades are deliberate: bump a line in `constraints.txt`, rebuild, test. `tests/test_dependencies.py` guards the driver and the lock.

Full server provisioning (Docker, nginx, certbot SSL, systemd unit, backup cron) is `sudo ./deploy.sh`. It uses `docker compose` v2 (`docker-compose-v2`) and stops the host nginx to free port 80.

Running services individually for local dev (needs Redis reachable; set `DATABASE_URL`/`REDIS_URL`/`CELERY_*`):

```bash
gunicorn wsgi:app -k eventlet --bind 0.0.0.0:5000          # web (SocketIO needs the eventlet worker)
celery -A tasks.celery_tasks worker --loglevel=info -c 1   # task worker
celery -A tasks.celery_tasks beat   --loglevel=info        # scheduler (see gotcha below)
```

Tests live under `tests/` — pure logic + SQLite API tests, no browser, LLM, Redis or Postgres (`conftest.py` forces SQLite in a tmpdir before importing the app). There is no venv in the repo and pytest is **not** in `requirements.txt`, but the runtime image has every other dependency, so the working commands are:

```bash
docker compose run --rm --no-deps web sh -c "pip install -q pytest && pytest tests/ -q"                      # whole suite
docker compose run --rm --no-deps web sh -c "pip install -q pytest && pytest tests/test_ai_registry.py -q"   # one file
docker compose run --rm --no-deps web sh -c "pip install -q pytest && pytest tests/ -q -k canvas"            # one test
```

Remember the image bakes the code in: **rebuild before testing** (`docker compose build web`) or you test the previous version. There is still no linter config. Verifying browser behaviour still means running the stack and watching `celery_worker` logs / the dashboard.

## Architecture

### The pipeline (read `tasks/celery_tasks.py` first)

The whole product is a Celery task chain. Each task takes `space_id` as its **first positional argument** and self-chains to the next stage:

```
fetch_contests(space_id)            ContestScraper       → auto-chains analyze_all_pending
  └ analyze_all_pending(space_id)   (fan-out)            → one analyze_contest per pending contest
      └ analyze_contest(sid, id)    ContestAnalyzer      → chains generate_designs
          └ generate_designs(sid,id) ImageGenerator      → chains run_submissions (if auto_submit_enabled)
              └ run_submissions(sid) ContestSubmitter
```

**Submissions and bids are paced chains, not one long task.** `run_submissions` / `submit_proposals` each handle **ONE** item per invocation and re-schedule themselves with `countdown=interval` while work remains (`submission_interval_minutes` / `project_bid_interval_minutes`, both default 5). With `--concurrency=1` a 5-minute sleep inside one task would pin the only worker for hours — no analysis, no generation, and for projects the Space's `browser_lock` held throughout; chaining frees both between items. A Redis marker `chain:{submit|project_submit}:{space_id}` names the live chain: a second manual trigger is refused rather than halving the interval, and `/api/stop/<group>` deletes the marker so a link already in flight won't schedule another. `_chain_refresh()` extends the marker only while it still holds this chain's session id (`SET … XX`) and returns False otherwise, which ends the chain — the old unconditional `SET` re-created a marker deleted mid-submission, so a Stop pressed while an entry was being posted was silently undone (live, 2026-09-23). `interval_seconds()` treats the configured value as a **floor** (up to +15% jitter, never less), and the interval only applies after an item that actually posted — a skip (no designs, closed contest) moves on in 15 s.

**Beat-driven jobs (projects).** `celery_beat` (scheduler class `tasks.celery_tasks:HeartbeatScheduler`, which also stamps `scheduler:beat_heartbeat` in Redis every 30 s) sends only two ticks: `tasks.project_discovery_tick` every minute and `tasks.cleanup_expired_projects_all` every 15 min, both with `expires` so ticks that queued behind a long task are dropped. The *schedule itself is per-Space data* (`project_discovery_*` settings) read by the tick — see "Daily discovery" below. The old 6-hourly `fetch_all_spaces` contest entry was removed from `beat_schedule` on purpose: beat had never been deployed, and starting it with that entry would have begun chaining contest analysis → generation → auto-submission (`auto_submit_enabled` defaults true) unasked. The task still exists for manual use.

`Contest.status` walks `pending → analyzing → generating → submitting → submitted` (or `failed`/`skipped`/`blocked`) and gates each stage — a task refuses to run if the contest isn't in the expected status. The "Start Bot" dashboard button calls `analyze_all_pending`, which also re-dispatches `generate_designs` for any analysed contest left `generating` with no message in the broker (after a Stop or a lost message) — `_queued_generation_ids()` reads the `celery` list and kombu's `unacked` hash, and a duplicate is harmless because the generator refuses a contest that is no longer `generating`. `fetch_all_spaces()` is the Celery-beat entry point that fans `fetch_contests` out across all Spaces every 6h.

Each `bot/` class is the worker for one stage and is independently triggerable from the API (`/api/contests/<id>/analyze`, `/generate`, `/submit`):
- `bot/scraper.py` — listing + detail scrape and attachment download. Resilient by design: a bounded 45 s Selenium command timeout + `_driver_alive()`/`_restart_driver()` self-healing (rebuild + re-auth, reaping orphaned Chrome) recover a wedged chromedriver mid-run instead of hanging on 120 s socket reads; listing pagination early-exits when a page adds no new links; the detail loop stops after 6 consecutive contests older than the freshness window (`max_contest_age_hours` setting, default 24, 0 = no limit), since the listing is newest-first.
- `bot/attachments.py` — deterministic (no-LLM) `AttachmentProcessor` that turns a contest's downloaded files into one `attachment_summary` dict consumed by the analyzer. Extracts PDF (all pages + scanned-PDF detection), DOCX (paragraphs + tables + embedded-image count), TXT, PPTX (slides + notes via stdlib zip/XML — no extra dep), and safely unpacks ZIP (zip-slip guarded, file/size capped, one level deep). Triages reference images (Pillow metadata + relevance selection, top picks at `detail:"high"`). Every parser is crash-proof: a corrupt/oversized/unsupported file is logged and recorded, never raised.
- `bot/llm.py` — `LLMClient`: the single chat/text/analysis gateway shared by the analyzer, critic, art director, project analyzer and submitter. One `chat(system, user_content, …) -> str` hides SIX documented wire shapes, selected per model by the registry's `transport` (or, for APIMart chat, by the model's `protocol` parameter — `ActiveConfig.protocol/transport/endpoint_url()`): `openai_chat` (`POST /v1/chat/completions`), `openai_responses` (`POST /v1/responses`, `instructions` + `reasoning.effort`), `anthropic_messages` (`POST /v1/messages`, top-level `system`, `{` prefill for JSON), `kie_codex_responses` (`POST /codex/v1/responses`, `input_text`/`input_image` parts), `apimart_chat` (Chat Completions with STRING content — images are dropped with a notice naming the protocol —, `stream: false` always, no `response_format`, stop ≤ 4) and `apimart_responses` (system/user input items of `input_text`/`input_image`, `max_tokens`, optional `web_search`). APIMart models omit `top_p` at its default and never re-send after a READ timeout (`retry_read_timeout: False` → `_maybe_billed`: the request may have completed and been billed; a connect timeout is still retried), and their only fallback is the operator's explicit same-provider `fallback_model` (off by default). Callers build OpenAI-style parts and get a plain string back. Models whose provider doesn't document vision get their image parts **dropped with a throttled warning** rather than sent blind; models without native JSON mode get a JSON instruction appended and fences stripped. Per-call arguments (a stage's `temperature=0.2`, `reasoning="low"`, `tools=False`) win over configured parameters, except `max_tokens`, which is a hard ceiling — a configured ceiling below ~3000 truncates brief-analysis JSON. `tools=False` vetoes a configured `web_search` for that call — the vision pass, condensation, Art Director and critic use it (a rewrite or a score gains only latency from a web search); the brief analysis keeps the operator's setting. The request lifecycle is `validate → health guard → send → classify → parse`, and **it never returns None**: every failure raises `ProviderCallError` carrying a normalised `ProviderError` (see "AI error handling" below).
- `bot/analyzer.py` — "Brief Intelligence Engine": a kie.ai LLM (via `LLMClient`) does text+vision to decompose the brief into a rich structured JSON analysis (`contest_type`, `brand_name`, `required_text`, `must_include`/`must_avoid`, `preferred_colors`/`forbidden_colors`, `risk_flags`, `deliverables`, `submission_description`, …) stored on `Contest.prompt_data`. It still emits the legacy keys the rest of the pipeline reads — `image_prompt`, `style`, `colors`, `mood`, `aspect_ratio`, `win_score` — via a compatibility mirror in `_normalize_brief`, which also supplies fallback defaults so a malformed model response never breaks the pipeline. Long briefs are condensed (requirement-preserving) instead of truncated at a fixed char count. **Analysis v3** (`ANALYSIS_VERSION = 3`) adds the plan an image model needs: `deliverable` (what the ONE submitted image must show — e.g. "the four race bibs side by side on one board"), `copy_blocks` (every word in reading order; required_text always merged in), `brief_facts` (what any wording must agree with), `layout_plan` (ordered zones), `placeholders`, `concepts` (3-5 distinct ideas, first = most literal), `reference_roles` (per image: `include_as_is` / `edit_base` / `style_reference` / `ignore`) and `text_density`. Older analyses stay valid — the builder and Art Director fill the gaps from the brief text. `_safe_json_loads()` repairs a body that starts at the first key (kie GPT-5.5 dropped the opening `{` for contest 188, and the whole analysis was discarded), and an `unknown`/`other` type is re-inferred from the title (`prompt_builder.infer_contest_type`). **Analysis v4** (`ANALYSIS_VERSION = 4`) is **grounded in the client's own material** (`client_sources()`: title, whole brief, document text, vision notes — never the condensed brief): `required_text` the brief never contains moves to `unverified_text`, a `brand_name` that occurs nowhere is dropped (`brand_name_unverified`), and every copy block carries `source: "brief" | "designer"` — `prompt_builder.is_grounded()` matches case/punctuation/spacing-insensitively and phone digits. Briefs up to 15,000 chars go in whole (the old 6,000 limit condensed long briefs into 1,400 tokens and lost lists). **A contest that forbids AI-generated work is `skipped`** (setting `contest_skip_no_ai`, default true): `detect_ai_prohibition()` runs free on the description BEFORE any paid call, and after analysis on the documents too, or on the model's `ai_policy: prohibited` only when its `ai_policy_quote` is grounded. The patterns fire on prohibitions only ("No AI.", "AI-generated designs will be rejected", "designers must not use AI", sin IA / sans IA / بدون ذكاء اصطناعي) — "a logo for our AI startup", "no AI clichés", "our app does not use AI" are subjects, not rules. Every entry is declared AI-generated, so entering such a contest pays for designs the client has already ruled out.
- `bot/prompt_builder.py` — deterministic (no-LLM) `CreativePromptBuilder` that turns `prompt_data` into GPT Image prompts, following OpenAI's GPT Image prompting guide (cited in the module docstring): short labelled sections in the order deliverable + intended use → concept → composition → layout zones → placeholders → TEXT → typography → colour → style → must-include → references → facts → quality bar → AVOID. Per-deliverable templates (logo, brand identity, web page, hero, app UI, banner, print, social, packaging, apparel, card, cover, document, presentation, character, illustration, product, vehicle, generic), each with its own **text policy**: `exclusive` (logo/shirt/cover — only the listed words, name spelled letter by letter), `layout` (web/print/packaging — the listed copy plus the minimum labels a real layout needs, never invented facts), `none` (illustration). **There is no negative-prompt block any more**: GPT Image has no such channel, so the old ~30 diffusion keywords ("jpeg artifacts", "duplicate logos") were just more things mentioned; exclusions are short plain rules. The old "add NO other words" line on every design is gone too — right for a logo, impossible for a homepage, and the model answered it by writing its own copy (contest 174 said "Founded in 1992" for a firm trading since 1998). Code/file requirements ("one HTML file with inline CSS", "editable source") are filtered out of the image prompt. A "website hero" analysis that asks for the whole page uses the full-page template (9:16). Client text is kept verbatim (`_verbatim`, trailing full stops included), and required_text is always rendered even when `copy_blocks` omits it. **Required text is never cut to a generic list cap** (80, a runaway guard): contest 182's flyer credited 32 people, the old 12-item cut kept 9, and the image model filled the gap with invented names — including real jockeys from elsewhere. Runs of ≥3 same-role items render as one quoted list line. **The canvas follows a stated size** (`ratio_from_dimensions`: "1200x628" → 16:9, "1500 by 500" → 21:9, A4 → 2:3, landscape flips) — only for templates whose image IS the deliverable (`_DIRECT_CANVAS`); a business card's "3.5 × 2 in" says nothing about a front-and-back board. The ratio vocabulary includes 5:4 and 21:9. On an exclusive-text design (logo/cover/shirt) a `source: "designer"` block never renders, Art-Director-supplied wording must be grounded in the brief (`sources=`), and `_scrub_art()` deletes quoted words in the Art Director's segments that are not in the text plan (`a ribbon reading "Est. 1998"`). `about_the_image()` / `canvas_ratio()` / `deliverable_text()` / `layout_zones()` expose the builder's view so the critic and auto-refine use the same plan. **A logo entry is one logo**: for the logo template the builder ignores the analysis's deliverable, layout zones and aspect (square unless the brief gives dimensions) and drops presentation-type must-includes — contest 185 ("six logo directions") came back as a 16:9 board, contest 259 ("a small monochrome version beneath") drew its wordmark twice. Several directions become `concepts`, one per variation.
- `bot/art_director.py` — `ArtDirector`: optional LLM stage (per-Space `prompt_enhancer_enabled` setting, default true) between the prompt builder and the generator. ONE JSON-mode call per contest (`reasoning="medium"`, `tools=False`, the original brief text included) returns craft **segments** per variation — `concept`, `composition`, `typography`, `color_usage`, `finish` — that `builder.render()` slots into its fixed template. The model never writes the final prompt, so a bad answer can only weaken the craft, never drop a requirement or change the client's text. For pre-v3 analyses it also returns the missing `layout` / `copy` / `facts` (marked MISSING in its input); `builder.supplement()` accepts them only where the analysis has none, and for an exclusive-text design only a missing wordmark. Any failure (API error, bad JSON, a composition under 25 words) keeps the deterministic prompt.
- `bot/generator.py` — provider-independent orchestration: builds prompts via `CreativePromptBuilder` (+ `ArtDirector` refinement), hosts reference images, downloads results, writes `Design` rows (each stamped with its `variation_label`). Every HTTP call lives in `bot/image_providers.py`. `select_references()` filters and orders the contest's images by the analysis's `reference_roles` (the client's own asset first, then an image to redesign, then style references; `ignore` is never uploaded — all-ignored means text-to-image), and the prompt names each attached image by index and purpose. A provider task that fails with a transient reason ("Server exception, please try again later" — contest 257) is resubmitted once; a moderation refusal or a timeout is not. One `_generate()` covers both modes — the transport is chosen from whether any reference upload survived, so a failed upload degrades to text-to-image instead of failing. Also exposes `generate_refinement()` — one corrective design built from the best design's prompt + critic feedback, used by auto-refine; it uses the builder's canvas (a logo stays 1:1 even when the analysis said 16:9) and drops notes the template forbids (a logo "board"). **Variations are submitted together and collected in one loop** (`_run_batch`, `transport.poll_once()`): three variations cost one render time on the single worker. A transient task failure is resubmitted once inside the batch; an account-level stop ends submission but the variations already rendering are still collected — it is raised (contest `blocked`) only when nothing was made. **Every download is opened before it becomes a Design**: an HTML/JSON answer, a truncated or unreadable file is refused, PNG/JPEG keep their real extension, anything else (WEBP) is converted to PNG for the upload form. Design files get a random suffix (`design_{n}_{hex}.png`) so a re-run never overwrites files older rows point at.
- `bot/image_providers.py` — one transport class per provider wire protocol (`KieImageTransport`, `ApidotImageTransport`, `PoyoImageTransport` — APIDot's contract on api.poyo.ai —, `KovapiImageTransport` — OpenAI-style jobs —, `ApimartImageTransport` — flat-body tasks for `gpt-image-2.5-flare|sunburst` and `gpt-image-2.5-ext` + `version`) behind `build_payload` / `submit` / `poll_once` / `await_result` / `host_reference` / `status_request`. **A callback URL is only sent to a public address** (`is_public_url`; PoYo also needs HTTPS): the dev default `http://localhost:5000` can never be reached and KovAPI rejects such a submit (`invalid_callback_url`); a refused callback is dropped and the job resubmitted. A status endpoint answering 401/403/404 three times in a row fails the task (`STATUS_STRIKES`) instead of holding the worker for TASK_TIMEOUT. **GPT Image 2.5's canvas rules** (APIDot and PoYo document the same: `auto` only at 1K; custom W×H only at 2K/4K, multiples of 16, edge ≤ 3840 which needs 4K, ≤ 3:1, 655,360–8,294,400 px; transparent needs PNG/WEBP) are enforced on save (`ai_registry.apply_constraints`, inside `validate_params`) and again on the wire. KovAPI: references inline as data URIs (`image_host.data_uri_for`, ≤ 1536 px), `quality` only at 1K, `auto` omitted (documented 1:1 default), a SAFE AREA prompt line when 1K centre-crops a non-1:1/3:2/2:3 canvas (`prompt_notes`), and `refine_error()` turns a 402 with a healthy balance into a key limit. `probe_generation()` is "Test model" for image-only providers (one job at each model's own cheapest declared values — APIMart spells its tiers `1k`, the others `1K`). APIMart: the `webhook` field is a BASE url (APIMart posts to `<base>/callback`, so the route is `/api/apimart/callback`), an accepted -ext task answers `{"code": 202, …}` (**any 2xx body `code` is a success** in `ai_errors`), task ids come back as `data[0].task_id` or `data.id`, an unknown id is HTTP 400 (counted as a strike), and references go through `POST /v1/uploads/images` (`ApimartFileUploader`). Its balance endpoint `/v1/balance` is the KEY's own quota (`balance_scope: "key"`, -1 = unlimited → `/v1/user/balance`), so `fetch_balance` blocks a used-up key as a key limit for free and a positive key reading also clears a key-limit block. Both providers are async and deliver the same two ways, so both share one wait loop: webhook → Redis (fast path) in parallel with status polling (fallback). `config_for_mode(has_references)` resolves text-to-image vs image-to-image — kie.ai and APIDot's GPT Image 2 both split the modes into separate model ids, so a contest with reference files would otherwise silently generate prompt-only art, and an image-to-image model with no references is rejected outright (`input_urls` is required). **The editing halves carry `selectable: False`**: the mode follows the brief analysis, so offering it as a choice only let an operator pick a mode the pipeline would override. They stay in the registry (the pipeline resolves them), are filtered out of the picker, and `selectable_equivalent()` maps a Space saved on one back to its entry model. `build_payload()` is registry-driven, not a fixed field list, because APIDot's image models do not share one (GPT Image 2.5 documents `background`/`output_format`; GPT Image 2 documents neither). `resolve_canvas()` validates the analyzer's per-contest aspect ratio against **that model's own** documented ratio list (Sunburst image-to-image documents 2:1 and 3:1; Flare does not) and moves an unsupported one to the nearest documented ratio (`nearest_ratio`, log-scale distance) — or `auto` when nothing is within ~1.5×, so a portrait brief is never forced landscape.
- `bot/critic.py` — `DesignCritic`: after generation, the configured chat model's vision (via `LLMClient`) scores each design against **the builder's plan, not the raw analysis** (a logo entry is judged as one logo; the expected text is every word the image was asked to carry, the wordmark included, and on exclusive-text designs extra lettering counts against it; overall score capped at 60 when text accuracy < 70; dense text reviewed at 1536 px) (overall / brief-match / visual-quality / text-accuracy, plus missing_requirements / visual_problems / risk_flags), persists `Design.critic_score` + `critic_json`, and picks the best. Runs in the `generate_designs` task (gated by the `design_critic_enabled` setting) and is crash-proof (neutral fallback per design; returns None on total failure). **Auto-refine** (`_maybe_auto_refine` in `tasks/celery_tasks.py`, per-Space `critic_regen_threshold` setting, default 55, 0=off): when EVERY design scores below the threshold, ONE extra "Critic refine" design is generated with the critic's missing_requirements/visual_problems folded into the prompt, then the whole set is re-scored — guarded to run at most once per contest.
- `bot/submitter.py` — Selenium submission flow with human-behavior simulation (random delays, per-char typing, mouse movement). Submits the **best-scored** design (`ORDER BY critic_score DESC NULLS LAST, variation_number ASC`), falling back to variation order when uncritiqued. Three live-verified rules, each of which had silently broken every submission (2026-09-18, 0 submitted / 27 failed — debug snapshots under `storage/designs/<id>/debug/`):
  - **The submission agreement checkbox is OPTIONAL.** Freelancer removed `fl-checkbox[fltrackinglabel="SubmitEntriesAgreement"]` from the entry form — the live DOM has only the HIGHLIGHT and SEALED upgrade boxes and no "agree"/"terms" text, while `Freelancer/submit_entry_page.html` still shows it. Requiring it aborted 29 submissions that were otherwise valid. A checkbox that IS present but refuses to tick is still fatal.
  - **The entry title is capped at 50 characters** (`entry_title_for()`). Titles are stored as URL slugs with the id appended ("Meaningful-Brand-Identity-for-Motor-Yacht-Grace-Happens-2787410", 62 chars); the form rejected that with "Please enter at most 50 characters." and went invalid. The helper drops the trailing id, turns hyphens into words and cuts on a word boundary.
  - **The AI use declaration is REQUIRED** (added by Freelancer 2026-09-23: `fl-radio[fltrackinglabel="AiDeclarationRadio"]`, inputs with random id prefixes and stable suffixes `--none` / `--partial` / `--full`). Without it the form refuses the submit with "Please declare the level of AI use for your entry." — the first paced run that day went 0 submitted / 17 failed on exactly that. `_declare_ai_use()` ticks the answer from the `submission_ai_declaration` setting: `full` = AI generated (default — the accurate answer for this bot's images), `partial` = AI assisted. **"No AI" (`none`) is never sent** — it would be false, and Freelancer disqualifies inaccurately declared entries; `ai_declaration_choice()` maps any other value to `full`. A present section that won't take the answer raises `AiDeclarationError` (no entry goes out undeclared); an absent section is fine.
  - **Descriptions promise nothing that was not made.** The entry is one generated PNG, but analysis-time descriptions promised "the editable Illustrator source along with SVG exports", "layered PSDs", "STEP/STP files" (15 of 80 queued). `honest_description()` drops any sentence claiming files, formats, deliveries or hand-work before it is typed; the analysis and fallback prompts no longer ask for it.
  - **A closed contest is `skipped`, never `failed`.** `_closed_marker()` reads the page for `CLOSED_CONTEST_MARKERS` ("the winner has been chosen", …) before hunting the CTA, and raises `ContestClosedError`, which `submit_design()` never retries. A contest can be awarded long before its deadline, so the stored deadline is not a reliable signal — contest 14 had 15 days left and a winner already chosen.
- `bot/auth.py` — cookie-based Freelancer login, shared by scraper and submitter.

### Projects / Proposals workflow (normal Freelancer projects)

A second, parallel pipeline for normal projects lives beside the contest one. Three user actions on the `/projects` page map to Celery tasks (each `space_id`-first, with `task_project_*_status` flags and `/api/stop/project_*` groups):

```
fetch_projects(space_id)              ProjectScraper    → queues analyze_all_projects (project_auto_analyze)
  analyze_all_projects(space_id[,ids][,limit]) (fan-out)→ one analyze_project per 'fetched' project, freshest first
    analyze_project(sid, id)          ProjectAnalyzer   → analysis + score + pricing + duration + proposal + review
  regenerate_proposal(sid, id)        ProjectAnalyzer   → a new proposal from the stored analysis (cheap)
  submit_proposals(space_id[,ids])    ProjectBidder     → real bid submission for 'approved' proposals only
```

**Only `submit_proposals` places bids, and only the two submit API routes ever enqueue it** — fetching and analysis never can. `Project.status` walks `fetched → analyzing → (approved | draft_ready | skipped) → submitting → submitted` (plus `failed`/`closed`); transitions are validated by `app.models.PROJECT_STATUS_FLOW` and worker_ready rescues in-flight rows. `discovered`/`fetching` are legacy (extraction files a project in one step) and `needs_review` is retired; all stay in the enum so old rows load. A finished analysis lands on `approved`, or on `draft_ready` when `project_require_approval` is true — **or always when the draft still carries an integrity problem** (see below). Quality concerns (weak review, bid below the economic floor, low score, an LLM "review" verdict) go on `analysis["concerns"]` and are logged as `⚠ Ready with concerns (…)` without blocking. Key modules:

- `bot/freelancer_api.py` — `FreelancerAPI`: thin `requests` client for the JSON API the website itself calls, authenticated with the Space's uploaded cookies. **Read its docstring before touching extraction.** It replaced Selenium scraping after an audit of 598 rows on 2026-10-30 found: `client_country` NULL on 598/598; `posted_at` NULL on 466/598 and never under 4 days old; "Closed" stored as a *skill* on 113 rows (`fl-tag` matched the header's status pill, so closed projects read as open); 100/100 "attachments" were the site's 69 KB HTML shell (`a[href*='/download']` matched the mobile-app nav link; real attachments are buttons with no href); 404 cards stored as titles; and a listing read before hydration returning 49 identical shell links on every page, which the scanner took for "end of results". One 100-row call replaces ~25 minutes of renders and needs no Chrome. Limits are published in response headers (`ratelimit-limit: 200, 200;window=60, 1000;window=3600`); `get()` retries 429/5xx/network, never retries 401 (`SessionExpiredError`) or a web page where JSON belongs (a possible wall — reported, never bypassed). `search_filters_from_url()` maps search-page URL params to API params **as captured from the site's own requests** (`projectSkills→jobs[]`, `types→project_types[]`, `q→query`, `projectFixedPriceMin→min_price`, …) and reports any it can't translate rather than silently widening the search. Pure helpers are unit-tested with live-shaped payloads (`tests/test_project_extraction.py`). **`is_project_open()` reads `status`, not the frontend label**: a lapsed project reads `status=frozen, frontend_project_status=open`. `recheck_stored()` closes rows waiting on analysis or a bid that have since closed, been bid on by hand, or aged out, before they cost anything (and frees their files — the host's disk is shared). `scan_listing()` de-duplicates by id, because paging repeats rows when projects arrive mid-scan (11 of 1,408 live), and stops early only when a whole page is past the age window, because the order is newest-first apart from a few promoted rows. The domain gate (`proposal_engine.domain_verdict()`) still classifies by FIELD from `DOMAIN_KEYWORDS`, and an excluded field beats an accepted one. Currency exclusion is enforced here and again in `analyze_project`. Budget minimums compare in dollars via the API's exchange rate. Rows skipped by a filter (`raw_meta.filter_skip`) are re-evaluated next run so relaxing a setting takes effect; a person's or the analysis's skip is never undone. **Images are recorded by name only** (analysis reads documents, not pixels; the first real run pulled 38 MB of photos for 41 projects). Documents go in a random `attachments-<token>` folder under the project's: nginx serves `/storage/` without login, so a client's file must not sit at a guessable address (it has no autoindex; `recheck_stored()` globs `attachments*` when freeing them). The module keeps a few page-text helpers (`parse_budget`, `detect_bid_restriction`, `detect_already_bid`, `_CLOSED_MARKERS`) because the bidder still reads the live page. **Already-bid text detection must stay strong-phrase-only**: the standard pre-bid form shows "You will be able to edit your bid until the project is awarded to someone." to every visitor, so substring markers false-positive nearly every open project (91/113 on 2026-07-13). Every run writes a summary to `project_last_fetch_json`, shown on the page.
- `bot/freelancer_profile.py` — the real Freelancer.com profile as the source of what a proposal may claim: tagline, about text, skills, track record, experience, education, certifications, portfolio, client reviews, read from the endpoints the profile page itself calls and stored per Space in `freelancer_profile_json` (refreshed after 12 h, retried at most every 30 min after a failure). It replaced the `profile_skills` / `profile_portfolio` / `profile_excluded_work` / `profile_tone` settings, which duplicated the profile and drifted from it (their old rows are simply unread). `profile_title` / `profile_summary` remain as optional additions. **Three degradation levels, none of which stops the pipeline**: readable → use it; unreadable with a snapshot → keep using it and show the error; nothing available (`source: "none"`) → the writer is told to make no claims at all. `render_profile()` states empty sections as "none listed — never claim any" so the model can't fill them in, and shows only the portfolio items and reviews closest to the project (23 items is enough to make it cite a logo job on a Python brief). `profile_fact_text()` is what the claim validator searches.
- `bot/proposal_engine.py` — PURE deterministic money/logic layer (no Flask/LLM imports): `recommend_bid` (avg-bid −20% default, budget clamps, economic floors, risk buffer, natural rounding), `estimate_duration` (work components → days + buffer), `compute_opportunity_score` (weighted multi-factor, max weight 22% so nothing dominates), `domain_verdict`, and `validate_proposal`, which separates **integrity** problems (unsupported years / counts / percentages / ratings / credentials / team claims, guarantees, unknown URLs, off-platform contact details, placeholders — never acceptable to send) from **style** problems (length, formula openers, AI filler, markdown, stating the bid or delivery time, no closing invitation). Claims about the freelancer are checked against the profile only: a brief asking for "5 years of experience" can't make that the freelancer's claim, though a number from the brief may be echoed as a plan. `check_style=False` for a person's edits: they answer for their own tone, but integrity still applies. `repetition_problems()` catches a draft starting or ending like recent proposals — **48 of 85 proposals opened "The key…" and 7 "The tricky…"** before this, and once openings were fixed 12 of the first 18 bids ended "Message me here on Freelancer and I'll walk you through…". Three shared words only count from `_FORMULA_REPEATS` earlier uses, because rewriting over a single match of something ordinary ("If you reply") cost about 35 extra drafts in one run; resembling other bids earns a retry but no quality warning. `clean_model_text()` undoes model leftovers (a literal `\\n`, `</escape>` after the answer, both seen live) and `split_into_paragraphs()` breaks up a solid block without changing a word. The LLM only supplies assessments; code decides numbers and eligibility.
- **Proposal writing was rebuilt from a study of 1,230 competitor bids and this account's 41** — read `docs/PROPOSAL_STRATEGY.md` before changing the writer, the reviewer or the style checks; each rule cites the habit it targets. Analysis is **v4** (`ANALYSIS_VERSION = 4`): confirmed requirements vs assumptions, constraints, `implementation_considerations` (point + why), `solution_options`, a paid `first_milestone`, `expected_outcome`, ≤ 2 `decision_questions`, `client_style` (formality, technical level, tú/usted/tu/vous) and `portfolio_match.fit` — only `strong` (the same kind of deliverable) may be cited as similar work and only it lifts the score; pre-v4 matches keep the old meaning (`strong`). The writer gets an opening move (diagnosis / constraint / decision / risk / outcome) and a closing move per project, a complexity-scaled length, and `overused_phrases(recent)` — four-word runs recurring in ≥ 3 recent bids. Style checks added in `validate_proposal`: "I'd start by / First, / Empezaría / Je commencerais / Hola / Estimado" openers, résumé lines ("My background includes…"), > 1 "rather than / not just", free-work wording (a profile name such as "…Free Sample Landing Page" is exempt), unrequested-work promises ("I'll first show you…"), durations not echoed from the brief, an extreme enumeration in one sentence (`is_deliverable_dump`: ≥ 4 commas and ≥ 8 list joints — calibrated so ordinary 3–4 item sentences pass), compound questions (multi-subject or glued; "A, B, or C?" passes), copying the brief, and es/fr invitation checks. `repetition_problems` also flags a middle sentence recycled from ≥ 2 recent bids. `tests/fixtures/proposal_pairs.json` holds eight real before/after pairs; the "after" texts are hand-written targets, not model output. Briefs now reach every stage whole (analysis 15k chars, writer 6k, reviewer 4k).
- `bot/project_analyzer.py` — confirms the project is still open and unbid (`_still_biddable`, a failed check proceeds rather than loses the project), then a structured-JSON analysis call that extracts what the writer needs: `client_problem`, `specific_details`, `approach`, `proposal_angle`, `sample_offer`. Then generate → validate → review → regenerate, at most `project_max_revisions` times, with history on `Proposal.revision_history_json`. The writer is steered per project (`_OPENING_MOVES`, `_CLOSING_MOVES`, recent openings and endings to avoid) because one fixed structure is how every bid became a template. A sample is offered only when the analysis calls it appropriate and the budget is at least `_MIN_SAMPLE_BUDGET_USD`. The review scores "would this client reply?" and lists `unsupported_claims` against the profile. **A draft that still has an integrity problem after its revisions lands on `draft_ready` with the reason in `skip_reason` — it can never reach the submit queue.** Honesty made the writer produce bids that talk the client out of hiring ("I recommend selecting a freelancer who…", live 2026-10-30), so three nets keep those from being sent: the analysis skips (`recommendation`, or `skill_fit` below `_MIN_SKILL_FIT`) before any writing is paid for; the writer can return `no_bid_reason` (skipped by `_skip_after_analysis`, or left unchanged on a rewrite); and the reviewer's `declines` counts as an integrity problem. A skip removes any earlier proposal. A draft that failed the deterministic checks never reached the critic, so the one going forward gets a critic pass at the end: its claims are still checked and its score is real. Dollar floors convert to the project's currency through the stored exchange rate. Reuses `AttachmentProcessor` via a duck-typed shim. `regenerate_proposal()` rewrites from the stored analysis and keeps a bid the operator edited.
- `bot/browser.py` — `BrowserSession`: shared authenticated driver lifecycle for the bidder only (the contest scraper/submitter keep their own proven copies — do not refactor them onto it casually). Includes `SecurityCheckError` (CAPTCHA/login walls are detected, never bypassed — the task pauses and tells the operator to fix cookies).
- `bot/project_bidder.py` — **waits for the page before reading it**: `_open_project()` waits up to 25 s for the rendered header and refreshes once if the Angular shell stays blank, then `_await_bid_section()` waits up to 40 s for the bid area's `fl-spinner[fltrackinglabel="PVPDetailsInitialisationSpinner"]` to go. It used to look once, 2–3.5 s after `driver.get()`: every "Bid form not found" of 2026-09-24 (42 of 43 bids that session, 61 in all) was a snapshot of the bare `<app-root>` shell or of that spinner — and the closed / already-bid / live-budget checks had been reading the same empty page and silently passing. **Restrictions are `skipped`, not `failed`**: `project_scraper.detect_bid_restriction()` reads the BID AREA's text only (`BrowserSession.bid_section_text()` — a brief saying "only experts can bid" is a wish, not a block). Then it fills `#bidAmountInput` / `#periodInput` / `#descriptionTextArea` (with formcontrolname/label/XPath fallbacks), re-reads the live budget before submitting, verifies success with positive signals only, saves evidence + submitted text/amount/period, honours the rolling-24h `project_daily_bid_limit`, and never marks anything submitted without verification. Duplicate protection: page-level "already placed a bid" markers + the API own-bid check at fetch and analysis + one-Proposal-per-project unique constraint + per-Space Redis `browser_lock`.

### Daily discovery (`bot/discovery_schedule.py`, `bot/project_discovery.py`)

- `discovery_schedule.py` is PURE time arithmetic (tested against real tz data in `tests/test_discovery_schedule.py`). Zones load from the **version-locked `tzdata` package** (`resolve_zone`), not the base image's `/usr/share/zoneinfo`: offsets change by decree — the tz database has Morocco on UTC+0 since 2026-09-20 — and stale system data would run "23:00 Casablanca" an hour off. A wall time inside a DST gap runs shifted past it, an ambiguous one at its first occurrence; `discovery_window()` = local midnight → min(now + 2 min skew, end of day).
- `project_discovery.due_runs(now)` decides, per Space, whether the latest slot needs a `DiscoveryRun` (`project_discovery_runs`). **The unique `(space_id, slot_key)` — slot_key is the local DATE — is the guarantee a day never runs twice**, whatever ticks race. Slots before `project_discovery_since` (set on first activation and whenever enabled/time/timezone change in Settings) are never caught up; a slot missed by ≤ 20 h is caught up (`trigger=catch_up`), older ones are reported as missed. `interrupted` (worker_ready marks running runs) and transient `failed` runs are re-armed with back-off up to 3 attempts; `stopped` (Stop button) never; a `queued` run with no broker message for 45 min is re-dispatched. `claim_run()` is an atomic queued→running UPDATE.
- `execute_run()` calls `ProjectScraper.run_full_fetch(window=(start, end), page_limit=N)`: the scan stops once a whole page is older than the window start, only projects whose `time_submitted` is in the window are filed, and the summary carries `stop_reason` and `coverage` — `complete` (end of results / read past midnight) or `partial` (page limit hit inside the day). Never report a partial scan as a total. Retry classification is `is_transient()`: network/5xx/rate-limit only; an expired session, a "web page instead of data" wall or a refused request waits for the operator.
- `tasks.daily_project_discovery` holds the Redis fetch lock `project_fetch_lock:{space}` (manual `fetch_projects` takes it too; it waits up to 30 × 2 min for a manual fetch), raises the `task_project_fetch_status` flag (the scraper treats the flag going idle as Stop), and queues `analyze_all_projects(space, eligible_ids, None)` — **no batch cap**: every eligible project of the day — when `project_auto_analyze` is on. Stop (`/api/stop/project_fetch`) kills it, deletes the lock and marks the run `stopped`; worker_ready clears stale fetch locks.
- Status for the UI: `scheduler_status()` (next run, last run, last success, heartbeat age → active / not_running after 180 s / unknown) and `day_stats()` (today by **publication** day in the configured tz). Endpoints: `GET /api/projects/discovery`, `POST /api/projects/discovery/run` (manual run, `trigger=manual`, `slot_key` NULL), `GET /api/projects/today` (dashboard). **Absolute times are formatted by the server** (`describe_local`); the browser only does relative times — Chromium's bundled tz data still put Casablanca on UTC+1 after the September 2026 change.

### Automatic cleanup (`bot/project_cleanup.py`)

- The clock is `Project.status_changed_at`, stamped by the `set` listener on `Project.status` in `app/models.py` (`active_history=True` — without it an expired-after-commit row looked "changed" on every re-file and its clock never ran out). Bulk `query.update(status=…)` bypasses the listener; don't add one for statuses.
- Deletes `skipped`/`failed` rows older than `project_cleanup_after_hours` (default 24), re-checked under `with_for_update(skip_locked=True)`. **Never** deletes a project with bid evidence: `submitted_*`, `submission_evidence`, `Proposal.bid_clicked_at` (committed by the bidder right after the Place-Bid click, before verification — a failed verification may still be a live bid), or a legacy error containing "could not be verified"/"already exists"; nor one with an `analyze_project`/`regenerate_proposal` message in the broker (the task passes those ids).
- Every deletion writes `ProjectArchive` (`project_archive`, unique `(space_id, external_id)`): the audit trail **and the tombstone** `run_full_fetch` checks so a removed project is never re-created or re-analysed (kept 60 days). A manual Delete in the UI leaves no tombstone, as before.
- Legacy rows were backfilled with `status_changed_at = updated_at` by `migrate_discovery_and_cleanup()` — never earlier than the real transition, so they expire late, never early.

Settings live in the `project_*` and `profile_*` keys (seeded in `_DEFAULTS`, editable on the Settings page). `project_detail_batch_cap` no longer limits page opens; it bounds how many projects one fetch sends to AI analysis automatically. Tests: `pytest tests/ -q` (SQLite, no browser/LLM; a scripted fake stands in for the API).

### AI Agents — providers, models and parameters as data

`/ai-agents` (`app/routes/ai_agents.py` + `app/templates/ai_agents.html`, operator guide in `docs/AI_AGENTS.md`) replaced the old "AI APIs" block on the Settings page. The page has four views — Overview, AI Tasks (Task → Provider → Model → Parameters → Test → Save, with a sticky save bar and an unsaved-changes guard), Providers (masked key, replace/remove, Test connection, Test model, balance) and Activity (`GET /api/ai/activity`: redacted AI log lines + breaker state) — and is rendered entirely from `GET /api/ai/registry`; every string from the server is escaped (base.html's `showToast` inserts raw HTML, so the page wraps it). **Green is earned**: a provider/task is green only after a live balance read or a passing Test; a saved-but-untested key is "Not verified". Test model on a task sends the on-screen draft `params` (`/api/ai/test-model` validates them like a save, then disables fallback for the probe).

- `bot/ai_registry.py` is the single source of truth: providers (`apidot`, `kie`, `poyo`, `kovapi`, `apimart`), models, and per-model parameter specs (type, enum values, default, min/max, tooltip, `wire` path, `show_if`). **Every parameter is one the provider documents** — a parameter a provider names but doesn't define (APIDot's `thinking` object) is declared `_unavailable(...)` and rendered disabled with the reason, so nothing guesses a schema. `validate_params()` clamps numbers, rejects unknown enum values, drops unknown keys; a malformed POST can never produce a payload the provider would reject.
- `bot/ai_config.py` resolves settings → `ActiveConfig` (provider + model spec + validated params + API key) and is the only module that reads the raw `ai_*` keys. `resolve()` raises with "API key … not configured" wording so `_is_config_error()` fails the item instead of retrying.
- **One provider per task** is enforced in three places: the model key carries its provider (`kie:gpt-5-5`), `save_config()` rejects a model whose provider doesn't match the submitted one, and failover only targets same-provider siblings. `tests/test_ai_registry.py` asserts it on the data itself.
- Parameters are stored per model (`ai_chat_params` = `{model_key: {...}}`), so switching models back and forth keeps each model's tuning.
- Adding a model = one dict in `MODELS` (+ a transport if it's a new wire shape). No UI change.
- **APIMart chat models are not in `MODELS`** — APIMart's catalogue is per KEY and publishes no per-model parameter schema. `bot/apimart_catalog.py` lists them (`GET /v1/models?expand=category&category=chat`, free; GPT/Claude ids only, image/embedding/audio excluded) into a per-Space snapshot (`apimart_chat_catalog`, tied to a key fingerprint — `save_provider_key` clears it), and `ai_registry.apimart_chat_spec()` builds a full spec per id (`apimart:<id>`, `dynamic: True`) with the documented protocol table (`APIMART_PROTOCOLS`) and family-specific params. `ai_config.lookup_model()` is the lookup that knows both kinds; `reg.get_model()` / `models_for()` see static models only (`serves()` / `providers_with()` include dynamic providers). Only a LISTED id can be saved; a saved id the list later drops still resolves to itself (`listed: False`, the page warns) and an unresolvable one raises a config error — never a silent switch. Public pricing (`/api/pricing/model`, no key sent, cached) supplies the per-1M-token rates shown and the `max_output_tokens` that bounds `max_tokens`. Routes: `GET /api/ai/catalog/apimart`, `POST …/refresh`, `POST …/pricing`. `_ai_canary` still pings only providers with REGISTERED chat models, so an image-only APIMart key keeps its image canary. Tests: `tests/test_apimart_chat.py` (mocked — no live APIMart inference has been run).
- Upgrades are seamless: `selected_model_key()` falls back to the legacy `llm_model` / `image_gen_model` values through `LEGACY_*_MODEL_MAP`, so a Space that only ever set `llm_model=gpt-5-2` resolves to a current model without anyone opening the page. `save_config()` keeps those legacy keys mirrored.

### AI error handling — categories, scopes, and the circuit breaker

Read `bot/ai_errors.py` first; it explains *why* each rule exists with the live response bodies that forced it.

**Never classify a provider failure by HTTP status alone.** Verified live on 2026-09-18, APIDot returns:

| condition | what it actually sends |
|---|---|
| insufficient credits | HTTP **400**, `error.type` = `invalid_request_error`, message `"Insufficient credits"` (and a second variant with `{"code":400,…,"type":"http_error"}`) |
| invalid key | HTTP 401, `type` = `authentication_error` |
| unknown model | HTTP 404, `code` = `model_not_found` |
| bad payload | HTTP **200** with `{"code":400,"error":{…"type":"validation_error"}}` |
| **key spending cap** (2026-09-22) | HTTP **429** `"Total credit limit exceeded: 200.12/200"` — `type` is `rate_limit_error` on the image route, `invalid_request_error` on chat — while `/api/user/balance` on the SAME key reads **653 credits** |

So `classify_response()` reads the HTTP status, `body.code` (which **outranks** it), `error.type`, `error.code` and the message text, and checks **billing by message before any type-based branch** — because the `type` field says `invalid_request_error` for a billing stop. Every failure becomes a `ProviderError` with:

- **category** — AUTHENTICATION / BILLING / RATE_LIMIT / INVALID_REQUEST / MODEL_UNAVAILABLE / TIMEOUT / NETWORK / UPSTREAM / PARSING / CONFIGURATION / UNKNOWN
- **scope** — request / model / provider / account
- **retryable** — only RATE_LIMIT, UPSTREAM, TIMEOUT, NETWORK. Billing, auth, bad payloads and unknown models are returned on the first attempt.

Two policy tables drive everything downstream:

- `MODEL_FAILOVER_CATEGORIES` = {MODEL_UNAVAILABLE, UPSTREAM, TIMEOUT, NETWORK} — the only failures where a sibling model of the SAME provider is worth trying, because each model family sits behind its own upstream route. **Billing, auth and rate limits are account-wide**: trying the sibling just burns a second doomed request, which is precisely what produced `LLM unavailable on APIDot · GPT-5.5 and APIDot · Claude Sonnet 5`.
- `PROVIDER_STOP_CATEGORIES` = {BILLING, AUTHENTICATION} — takes the provider out of service for the Space.

**The circuit breaker (`bot/ai_health.py`)** is what stops one dead account from costing 43 contests × 2 doomed calls. An account-scoped failure blocks the provider in Redis (per Space, TTL 15–30 min); `guard()` then fails subsequent calls locally with the real reason and **zero HTTP**. It is half-open — after the TTL one probe goes through — and clears on any success, on a key change, or on a balance check that shows credits. `preflight()` runs before a fan-out so `analyze_all_pending` refuses to dispatch 39 doomed tasks. Balance is read per provider and cached 5 min (the docs say not to poll it). **Two different shapes**, both verified live: APIDot `GET /api/user/balance` → `data.credits_amount` (an object), kie.ai `GET /api/v1/chat/credit` → `data` as a **bare number**.

**A capped KEY is not an empty ACCOUNT** (`ai_errors.KEY_LIMIT`, `ProviderError.is_key_limit`). It is BILLING by category — non-retryable, provider-stopping — but it differs in everything the operator sees and in how it clears: the message says to raise the key's limit (adding credits does nothing); the breaker holds it **24 h** instead of 15 min; a positive balance does **not** retire it (the balance was 653 the whole time); and the free Test Connection must not clear it or paint it green — only a real call (Test model, any success) or a new key does. Two ordering facts made it expensive on 2026-09-22: every `analyze_contest` task queues ahead of every `generate_designs` task, and no free check can see the cap, so 83 full analyses (~675 kie.ai credits) ran before the first generation hit the wall. Hence `_ai_canary()`: before a fan-out, `analyze_all_pending` sends one single-token chat ping on the IMAGE provider's key — or, for an image-only provider (PoYo, KovAPI, APIMart), one real 1K test image (`probe_generation`), skipped while a real submission in the last 6 h proved the key (`ai_health.note_verified` / `recently_verified`) — and `analyze_contest` refuses to spend on a contest while the image provider's breaker is open. KovAPI's 402 `insufficient_quota` covers balance, the key's daily budget, its total quota and a burst outrunning the pre-charge reserve; `KovapiImageTransport.refine_error()` calls it a key limit when the balance is ≥ 30 credits. Balance shapes are parsed by `ai_health.extract_credits` (KovAPI declares `balance_path: "balance.credits"`). The generator also re-raises provider-stopping errors from `_run_single` / `generate_for_contest` instead of logging "Variation 1 failed" and writing `failed`, so the task can park the contest.

**A contest that could not run is `blocked`, not `failed`** — the brief is fine, the account is not. `requeue_blocked_contests()` releases them when the provider works again — an already-analysed contest resumes at `generating` (so the chat provider isn't paid twice for the same brief), the rest go to `pending`; `tasks.celery_tasks.resume_blocked_contests()` wraps it and dispatches `generate_designs` for the resumed ones. Task events now carry an explicit `status` (`completed` / `skipped` / `blocked` / `failed` / `retrying`), which is what killed the self-contradictory `🧠 Analysis complete — error: Analysis returned None`.

**A provider response that cannot be read is an error, never a silent None** — `parsing_error()` raises `APIDOT_RESPONSE_PARSE_ERROR` with safe diagnostics (top-level keys, finish_reason, HTTP status) and no prompt or key material.

### kie.ai's GPT-5.5 route is unreliable — that is what its sibling is for

Measured live on 2026-09-18: **10 identical probes to `/codex/v1/responses` returned 3 successes and 7× HTTP 500** `{"error":{"type":"server_error","message":"Server exception, please try again later"}}`. Same key, same payload, same minute — so it is neither our request shape nor the account (652 credits available, and a failed call consumes none). It is genuinely flaky upstream.

Three consequences are baked into the registry:

- `kie:gpt-5-5` declares `fallback: "kie:gpt-5-2"`. GPT-5.2 sits behind a **different route** (`/gpt-5-2/v1/chat/completions`, the OpenAI-compatible shape) which answered **8/8** in the same window. Since UPSTREAM is in `MODEL_FAILOVER_CATEGORIES`, a 500 storm now self-heals: three fast retries, then the sibling, then `_degraded` sends the next ten minutes of traffic straight to the healthy route. Verified live end-to-end — `Kie.ai · GPT-5.5 failed (UPSTREAM) — falling back to Kie.ai · GPT-5.2` and the contest completed.
- **GPT-5.2 is the more reliable choice but not the default**, because the operator picks the model; the failover makes either selection safe. It is slower (8–17 s vs 2–3 s) but it has native JSON mode and vision, both verified live.
- `reasoning_effort` is **per-model**: GPT-5.2 documents `low|high`, GPT-5.5 documents `low…xhigh`, and APIDot's chat route documents none. `LLMClient._effort_for()` sends only a level the selected model declares, so a stage asking for `xhigh` degrades instead of being sent blind.

Two more kie.ai response quirks the classifier now handles: `/gpt-5-5/v1/chat/completions` (the wrong route for that model) answers **HTTP 200 with `{"code":422,"msg":"The model is not supported"}`, and `/claude/v1/messages` returns 503 while the GPT routes are fine.

### Multi-tenancy (Spaces) — the pervasive invariant

The active Space lives in `flask.g.space_id`, set by a `before_request` hook from the `X-Space-Id` header (XHR) or `cb_space` cookie. Space-scoped models (`Contest`, `Log`, `Setting`) declare `default=_current_space_id`, so new rows auto-stamp the current Space without callers passing it. **`Setting` has a composite primary key `(space_id, key)`** — every Space has its own independent copy of all settings, including API keys and Freelancer cookies. Celery workers have no request context, so every task body runs inside `_app_ctx(space_id)`, which pushes an app context and binds `g.space_id`. When writing queries, always filter by `g.space_id` (or `space_id=...`) — see the existing routes for the pattern.

### API keys come from the DB, not the environment

Keys are per-Space `settings` rows, entered on the **AI Agents** page (not Settings): `kie_api_key`, `apidot_api_key`, `poyo_api_key`, `kovapi_api_key`, `apimart_api_key` (seeded as secrets in `_DEFAULTS`). Only the provider a task is configured to use is ever read — `bot/ai_config.resolve()` fetches exactly one key. `openai_api_key` is a legacy row kept for backward-compat but **no longer read**; the `OPENAI_API_KEY`/`KIE_API_KEY` env vars in `config.py`/`.env` are vestigial defaults and are **not** what the bot actually uses. Same for `image_host_method`/`imgbb_api_key`: reference images always go to the selected provider's own file store (`bot/image_host.py`: `KieFileUploader`, `ApidotFileUploader`, `PoyoFileUploader`, `ApimartFileUploader`), because only a provider-hosted URL is guaranteed reachable from its generation servers — KovAPI has no store, so its references travel inline as data URIs (`data_uri_for`), which also keeps client files off guessable `/storage/` URLs.

### Image result delivery: callback first, polling fallback

Both providers are asynchronous and both are handled the same way in `ImageTransport.await_result()`: a webhook writes the result into Redis (fast path) while the provider's status endpoint is polled in parallel (fallback). Whichever answers first wins, so generation completes even when the webhook never arrives, and a failed task is detected promptly rather than waiting out `TASK_TIMEOUT`.

### Auth & request guards (`app/__init__.py`)

Single admin operator (`ADMIN_USERNAME`/`ADMIN_PASSWORD` in `config.py` — override via env in prod). Two `before_request` hooks run on every request: an auth gate (valid itsdangerous-signed token in the `cb_auth` cookie or `X-Auth-Token` header; JSON routes get 401, page routes redirect to `/login`) and the Space resolver. Public paths bypass both: `/login`, `/auth/*`, `/static/*`, `/storage/*`, `/favicon.ico`, and the provider webhooks in `_WEBHOOK_PATHS` (`/api/kie-callback`, `/api/apidot-callback`, `/api/poyo-callback`, `/api/kovapi-callback`, `/api/apimart/callback`). The frontend monkeypatches `window.fetch` in `app/templates/base.html` to attach both headers to every same-origin request and bounce to `/login` on 401 — so individual `fetch()` call sites don't manage auth.

### Real-time updates

SocketIO over a Redis message queue (`message_queue=REDIS_URL`) lets Celery workers emit events that reach browsers. Workers call `_emit()`; `app.models.add_log()` emits `new_log` on every log write. Events (`task_status`, `task_complete`, `new_log`, `contest_updated`, `manual_review_needed`, `config_error`) carry `space_id` so each browser filters to its own Space via `_forMySpace()` in base.html.

### Schema management

No Alembic migrations are used in practice. On startup `create_app()` runs `db.create_all()` + the idempotent `migrate_to_spaces()` + `seed_default_settings()` **for every Space**, the whole block serialized across workers by a **Postgres advisory lock** so concurrent gunicorn/Celery boots don't race. `seed_default_settings()` is per-key idempotent: adding a key to `_DEFAULTS` is enough — the next boot backfills it into all existing Spaces (no manual INSERT needed). The Celery `worker_ready` hook additionally rescues contests orphaned in an in-flight status by a crashed worker: `analyzing` → `pending`, and `generating` → `pending` **only when there is no analysis to resume from**. An analysed `generating` row keeps its status — its `generate_designs` message is still queued (or unacked, and redelivered), and resetting it made that message refuse to run and forced a paid re-analysis; a routine rebuild with 80 contests queued would have thrown away 80 analyses. One with no message left is resumed by Start Bot. `migrate_to_spaces()` hand-rolls the pre-Spaces → multi-Space upgrade (adds `space_id` columns, rebuilds `settings` with the composite PK, swaps the global `contests.url` unique constraint for a per-Space one). Schema changes generally go here, not in a migration file. Flask-Migrate is wired up but `migrations/` doesn't exist.

### Storage & static serving

Attachments and generated images live under `/app/storage/designs/{contest_id}/{attachments,generated}/`. They're exposed at the `/storage/<path>` URL — served directly by nginx (alias) in production, with a Flask fallback route for direct-to-`:5000` dev. `app/routes/api.py::_path_to_url()` converts a stored DB path into that URL; reuse it rather than building paths by hand.

## Conventions & gotchas

- **Scraper/submitter CSS selectors are confirmed against the live Freelancer Angular SPA** (saved DOM snapshots in `Freelancer/*.html`). They use stable `fltrackinglabel`/`fl-*` attributes. Do not change a selector without re-testing against the live site or a fresh snapshot — a silent selector break is the most common failure mode.
- **`nginx -t` fails while `web` is down** (`host not found in upstream "web:5000"`), and this one nginx also fronts the unrelated `growmaz` sites on the host, so never restart it to fix the app. A failed `nginx -s reload` is harmless: the running workers keep the old config.
- **Freelancer cookies** are exported from the Cookie-Editor browser extension as JSON and uploaded on the Settings page. The required auth cookies are `GETAFREE_AUTH_HASH_V2` and `session2`. `XSRF-TOKEN` is **not** required (it's a CSRF token, not an auth cookie — freelancer.com re-issues a fresh one to the browser on first navigation); it's injected when present but its absence never blocks upload/login. The required-cookie set lives in two places that must stay in sync: `app/routes/settings.py::_REQUIRED_COOKIES` (upload) and `bot/auth.py::REQUIRED_COOKIE_NAMES` (load).
- **Setting descriptions must fit `varchar(300)`.** `settings.description` is `String(300)`; SQLite ignores the length, Postgres does not, so an over-long `_DEFAULTS` description passes every test and then kills `create_app()` at boot with `StringDataRightTruncation` (it took the web app down for a minute on 2026-09-23). `tests/test_settings_keys.py::test_every_default_description_fits_its_column` guards it.
- **Adding a setting**: `app/models.py::_DEFAULTS` is the single source of truth — it seeds the row AND (via `DEFAULT_SETTING_KEYS`) makes the key saveable, because `app/routes/settings.py::_SAVE_KEYS` is *derived* (`_FIELDS ∪ DEFAULT_SETTING_KEYS − _INTERNAL_KEYS`). `_FIELDS` only controls label/input-type/secret, so forgetting a key there no longer makes the field read-only; you still need an `id="field-<key>"` input in `settings.html` plus its name in the `PLAIN_FIELDS` JS array. `_INTERNAL_KEYS` (cookies, `task_*` runtime state, `logs_cleared_at`, legacy `openai_api_key`, and every `ai_*`/provider-key setting owned by the AI Agents page via `bot.ai_config.MANAGED_KEYS`) can never be written through the form — an AI setting belongs in `bot/ai_registry.py`, not in `settings.html`. `/settings/save` returns any unknown submitted key in `ignored` and logs a WARNING — silent drops were how `project_detail_batch_cap` stayed uneditable for weeks while the page reported "saved". `tests/test_settings_keys.py` enforces the whole invariant.
- **Stopping tasks**: the `/api/stop/<group>` endpoint must SIGKILL workers and also drain the Redis broker list directly — graceful termination lets `self.retry()` re-queue the task and "Stop" appears to do nothing. See the long comment in `stop_group`. **Also drain the unacked set**: with `task_acks_late=True`, a task that was mid-execution when the worker died lives in kombu's Redis `unacked` hash, NOT the `celery` list — `celery purge` misses it and the next worker restart re-delivers and re-runs it (verified live: a purged-then-restarted worker resurrected a full generate→submit chain). To fully stop: stop worker → `celery purge -f` → `redis-cli DEL unacked unacked_index` → start worker. Conversely, to deploy **without** losing the task in progress: `docker compose stop -t 290 celery_worker` gives it a warm shutdown, while a plain `up -d` kills it after 10 s and strands its message in `unacked` for the one-hour visibility timeout. `_queued_project_ids` ignores `unacked` for this reason, so such a project stays eligible instead of showing "Analyzing… 1 left" for an hour.
- **Reference uploads are stored under a hashed, URL-safe name** (`image_host.storage_name()`: `<sha1[:12]>-<safe stem>.<ext>`) and **normalised first** (`generator.prepare_reference()`: long side ≤ 2048 px, palette/CMYK → RGB/RGBA PNG, transparency kept, original untouched). Both broke contest 257 on every attempt: `Journal #1 Postcard Content Side.png` went into the public URL raw and everything after `#` became a fragment ("Unable to fetch the image", first reported as a vague "Server exception"), and its 12,892 × 6,818 logo is far beyond what the edit model needs. The hash also stops two contests' `logo.png` overwriting each other in the provider's shared upload folder.
- **Reference uploads must set a multipart Content-Type.** `requests` defaults the part to `application/octet-stream`, and APIDot rejects that outright — `HTTP 400 {"message":"Unsupported file type: application/octet-stream"}` for a plain `IMG_1678.jpeg` (observed live 2026-09-18, and it silently degraded every contest to text-to-image). `bot/image_host.py::_mime_for()` types every part, and a 400/415/422 there is permanent so it is never retried.
- **`self.retry(exc=…)` re-raises the ORIGINAL exception when retries run out**, not `MaxRetriesExceededError` — catching only the latter leaves the chain marker and the `task_*_status` flag stuck on "running" forever. The paced tasks, `analyze_contest` and `generate_designs` all catch `celery.exceptions.Retry` (a retry IS queued) separately from the exhausted case (mark failed / release the chain). `analyze_contest` also resets the contest `analyzing → pending` before retrying: the analyzer only runs a `pending` row, so the retry used to log "expected 'pending'. Skipping." and strand the contest in `analyzing`.
- **Config errors don't retry**: if a task exception message contains "not configured" / "API key" / "settings" it short-circuits the contest to `failed` instead of flooding the queue with doomed retries (`_is_config_error`).
- **Celery beat is deployed as `celery_beat`** (one instance only; it needs no DB). If it is down, nothing daily happens and Settings/the dashboard say "Scheduler not running" (no heartbeat for 3 min). The schedule file lives in `/tmp` — every decision that matters is in Postgres (`project_discovery_runs`, `project_discovery_since`). With `--concurrency=1` a tick waits behind a long task; the run is then marked `catch_up` and still covers its whole day. A failed analysis now records `Analysis failed: …` in `skip_reason`, so the table and the cleanup archive say why.
- **`deploy/tls/` is in `.dockerignore`.** nginx bind-mounts it at runtime; copied into the app image it put `server.key` in every layer, and a root-only certbot directory (`deploy/tls/<domain>`, mode 0700) makes `docker compose build` fail with "permission denied".
- **Orphaned Chrome is reaped through `/proc`** (`bot.browser.reap_orphaned_chrome()`): at every driver start, in `worker_process_init` (a new pool child means the previous one died) and at `worker_ready`. An orphan is a browser process whose parent is PID 1 — its task was SIGKILLed (Stop) or crashed before `quit()`. The old cleanup called `pkill`, which this image does not have (no procps), and swallowed the error, so nothing was ever cleaned: on 2026-09-25 one leaked Chrome had rendered for 45 h (238 MB, 34 % CPU) on the 2-core / 1.9 GB host, next to 1,421 zombies, with swap full and load 14; killing it dropped the load to 0.6. The worker service also runs with `init: true` (docker-init as PID 1) so exited processes are reaped. `BrowserSession` uses `page_load_strategy = "eager"` (the renderer timed out at 30 s on map tiles and trackers) and waits for what it needs explicitly.
- `undetected-chromedriver` pins its driver to the installed Chromium major (`_detect_chrome_major` → `version_main`) because the apt-packaged Chromium lags stable; don't remove that pin.
